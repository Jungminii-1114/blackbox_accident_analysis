# Yejun 실험 브랜치

3-Stage 전부 베이스라인(MViT/ResNet+GRU) 대신 "라벨이 없거나 극소량이라 딥러닝 파인튜닝이
성립하지 않는다"는 판단 하에, Stage별로 다른 전략을 씀. 코드는 [`Baseline/`](Baseline/)에 있고
학습 노트북 → `model/` 저장 → 추론 노트북 → `inference.py` 생성 → `submit.zip`은 원본 베이스라인
구조를 그대로 유지(평가서버 인터페이스 안 건드림).

## 실제 제출 점수 vs 팀 베이스라인

| Stage | 팀 베이스라인(MViT/ResNet 원본) | 이 브랜치 | 가중치 | 비고 |
|---|---|---|---|---|
| 1 | 0.53397 | **0.316** | 0.2 | ⚠️ 베이스라인보다 나쁨 - 재작업 필요 |
| 2 | 0.11721 | **0.267** | 0.4 | 개선 |
| 3 | 0.14581 | **0.521** | 0.4 | 큰 개선 |
| **종합** | 0.212 | **0.378** | | 가중합 기준 |

Stage2·3은 방향이 맞았고, Stage1은 로컬 합성데이터 정확도(98%)가 실제 재녹화 영상에
전혀 일반화되지 않았다는 게 실제 점수로 확인됨(자세한 원인은 아래 가설 검증, Stage1 이슈 참고).

## Stage별 접근

### Stage 1 — 핸드크래프트 포렌식 피처 + 로지스틱 회귀 (재작업 필요)
- 재녹화 라벨이 5+5건뿐이라(그마저 재녹화 예제는 실제 재촬영이 아니라 합성 파생) 비디오
  분류기를 학습시키면 그대로 외운다. 대신 모아레 FFT 고주파, 화면 플리커, JPEG 이중압축
  블록 경계, 블러, 테두리 암부 5개 피처 + 로지스틱 회귀로 대체.
- 데이터 부족은 원본 영상에 모아레/플리커/이중압축/테두리를 합성 적용해 재녹화 클래스를
  대량 생성하는 방식으로 우회 (`stage1_recapture.py::simulate_rerecording`).
- **실패 원인 추정**: 합성 artefact가 실제 재녹화 artefact와 분포가 달라서(메인 README A6가
  정확히 이 위험을 지적함) 과적합. 실제 재촬영 데이터 없이는 이 접근의 상한이 낮음.

### Stage 2 — 모션에너지 충돌탐지 + COCO 탐지기 + 학습형 재정렬기
- `t_collision`만 실라벨이 있어서(나머지 3개 필드는 -1) 학습이 아예 불가능한 상태였음.
- **collision_frame**: 프레임간 화면 변화량(모션 에너지) 급증 지점. 라벨 5건 대비 MAE 2.4프레임.
- **entry_frame/entry_side/evasion_space**: COCO 사전학습 탐지기(fasterrcnn_mobilenet_v3)로
  상대차량 박스를 잡음. AIHub 교통사고 영상 데이터(597, 차대차 카테고리, 554영상/9085프레임)의
  실제 바운딩박스로 검증한 결과:
  - "가장 큰 박스 = 상대차량" 규칙: mean IoU 0.34, 적중률(IoU>0.5) 39%
  - 학습형 재정렬기(위치/크기/점수 6차원 MLP, 150/50 영상 train/val 분리, held-out 기준):
    mean IoU 0.334, 적중률 38.3% — oracle(후보 중 최선)은 0.51/63%라 아직 갭 있음
- 트래킹(프레임간 IoU 그리디)은 시도했으나 개선 없음(0.335, 사실상 동일) — 첫 프레임에서
  잘못 고르면 계속 따라가는 문제. 재정렬기가 유일하게 실측으로 검증된 개선.

### Stage 3 — Optical Flow 휴리스틱 (딥러닝 모델 없음)
- 라벨이 6초 간격 50개뿐 — 대신 이 문제 자체가 라벨 없이 풀림: 전방 optical flow만으로
  가감속(전진 flow 크기)과 조향(수평 flow 편향)을 직접 측정.
- AIHub 사고위험 환경 운전습관 데이터(71851, 사고다발구간, 10개 영상/native 30fps)의 실측
  CAN 센서로 검증:
  - 속도: 실측 `gps_vss` vs flow speed_proxy 상관계수 평균 **0.618**
  - 조향: 실측 자이로 각속도(`angZAve`, CAN의 `steering_angle`/`yawrate` 필드는 이 장비에서
    전부 0이라 못 씀) vs flow steer_proxy 상관계수 평균 **-0.519** (10개 영상 전부 동일 부호)
- 이 검증 과정에서 **좌/우 부호 버그**를 발견해 수정함(물리 추론 + 실측 상관관계 + 실제
  좌회전 차선 프레임 확인, 세 가지 교차검증). 수정 후 공개 라벨 50개 기준 정확도
  70.0% → 71.0%.

| ID | 가정 | 이 브랜치에서의 증거 |
|---|---|---|
| A1 | 도메인 갭(사설 vs 공개 영상) | Stage1 실제 점수(0.316)가 로컬 검증(98%)보다 훨씬 낮음 — 갭이 실재하고 큼을 확인 |
| A2 | Stage3 숨은 범주가 CAN 신호로 생성됨 | AIHub 실측 CAN과 flow 상관관계(0.618/0.519)로 **강하게 지지됨** — 라벨 생성 로직 추정이 맞는 방향 |

| A4 | Stage2 충돌 = 실제 접촉(위험 시점 아님) | 모션에너지 스파이크가 라벨 5건과 MAE 2.4프레임으로 잘 맞음 — **지지됨**(급격한 화면 흔들림 = 실제 충격) |
| A5 | Stage2 진입 = 바퀴의 차선 침범(첫 등장 아님) | 우리 "박스 첫 등장" 휴리스틱의 낮은 IoU(0.33)가 **이 우려를 뒷받침** — 메인 README의 V2(track+lane 침범 정의)가 맞는 방향일 가능성 높음 |
| A6 | Stage1 재녹화가 실제 artefact 포함 | 합성 전용 학습이 실제 점수에서 참패(0.316 vs 베이스라인 0.534) — **위험이 현실화됨**, 실제 재촬영 데이터 확보가 필수로 보임 |
| A7 | 60분/인터넷없음 제약 | 로컬에서 전체 파이프라인 실행 + submit.zip(0.067GB) 생성 확인, `weights_backbone=None` 안 하면 인터넷 필요한 버그 발견/수정. **GPU 환경에서 실제 시간은 아직 미측정** |
| A8 | Public 제출 과적합 방지 | 아직 1회 제출만 함, 판단 이름 |

## 다음 단계 제안 (메인 README 방향 반영)

1. **Stage1 재설계 최우선** — 합성만으로는 안 됨. 실제 재촬영 소량 확보(메인 README A6/V1)
   하거나, 최소한 group split(원본 clip 단위)로 합성 다양성부터 넓혀야 함.
2. **Stage2 V2(피해차량 track + lane 침범)로 업그레이드** — 지금의 "박스 첫 등장" 대신
   메인 README가 제안한 트래커+차선모델 기반 entry 정의로 전환. AIHub 597의 실제 bbox를
   더 많은 카테고리(현재 4개 카테고리만 사용, 나머지도 이미 다운로드됨)로 확장해서 재정렬기/
   tracker를 더 키울 수 있음.
3. **Stage3는 comma2k19/A2D2로 추가 검증** — AIHub 검증으로 접근 자체는 이미 강하게 지지됨.
   국내 도로가 아닌 해외 데이터라 A1 도메인갭 고려는 필요하지만, 표본을 늘려 임계값을
   더 안정적으로 보정할 수 있음.
